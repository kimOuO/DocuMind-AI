# 切塊方法對 Table 2 的影響

題目的第三題（`Performance of ablated versions of LightRAG`）要從論文的 Table 2 回答。固定長度切塊會把這張表切開。這個實驗量測每一種切塊方法把 Table 2 的 16 列切成什麼樣，作為 P3 處理驗收條件 AC-14 時的比較依據。

## 量測什麼

統一的量測程式 `measure_table2_rows.py` 對每一種方法算三個數字（Table 2 共 16 列）：

| 量測 | 意義 |
|---|---|
| 整列完整出現在至少一個切塊 | 數字沒有被切斷 |
| 整列與它的區塊標題同塊 | 看得出這一列屬於 LightRAG、-High、-Low 還是 -Origin |
| 整列與資料集標題同塊 | 看得出每一欄是 Agriculture、CS、Legal 還是 Mix |

三個都是 16/16 才算這個方法對 Table 2 沒有破壞。

## 方法與結果

每種方法一個結果檔 `<方法>.table2-rows.json`，檔內先是 `method`（說明與參數），再是 `measurements` 與該頁的切塊全文。

| 方法 | 檔案 | 整列完整 | 與區塊標題同塊 | 與資料集標題同塊 | 狀態 |
|---|---|---|---|---|---|
| 固定長度 400 tokens、重疊 80、逐頁（P2 的實作） | `fixed-size-400-80.table2-rows.json` | 16/16 | 14/16 | 6/16 | 基準（2026-11-05） |
| 檢索到的切塊連同前後相鄰的切塊一起交給 LLM | 未實作；由基準檔推算 | 16/16 | 16/16 | 12/16 | 候選做法 1，未採用（見下） |
| 表格區域不切開、獨立成一塊（P3 的實作） | `table-region-400-80.table2-rows.json` | 16/16 | 16/16 | 16/16 | **採用**（2026-11-06，ADR 0007） |
| 表格另存逐列改寫的文字 | 未實作 | | | | 候選做法 3，未採用（見下） |

**候選 1 的推算**：以基準檔的切塊 #24、#25、#26 為例，檢索到 #24 時連同相鄰的 #23、#25 一起送出，可補回 `-High` 被切到 #25 的兩列與它的區塊標題，但 `-Origin` 的四列在 #26，仍拿不到（只有檢索到 #25 或 #26 時才會連帶納入 #26），所以「與資料集標題同塊」最多 12/16。另外每個檢索結果變成三塊：K＝5 時證據量最多 15 × 400 ＝ 6,000 tokens，超過 5,500 的證據預算，必須再丟掉一部分。

**候選 3 未採用的原因**：逐列改寫成句子需要解析表格的結構（哪幾欄是哪個資料集、哪幾列是哪個版本），這是針對 Table 2 版面的規則，換一張表就要重寫；候選 2 的量測已經三項 16/16，沒有必要再加一層。

- 記錄日期：基準 2026-11-05；表格區域 2026-11-06
- 設定：每塊 400 tokens、重疊 80、逐頁不跨頁；PDF 以 pypdf 解析
- 標準答案（128 格）：`../ground-truth/paper-structure.json`
- 重新產生目前方法的結果：`.venv/bin/python evaluation/table2-chunking/measure_table2_rows.py`（讀 `.env` 的 `CHUNK_SIZE`、`CHUNK_OVERLAP`）

## 採用的做法：表格區域獨立成塊（`app/ingestion/tables.py`）

- 區域從 `Table N:` 的標題行開始，接著是表頭行（短、沒有句尾標點）與數字列（一行內四成以上的詞是數字或百分比），到第一行內文為止。只有「有標題且有數字列」才算表格；第 9 頁的案例表（Table 3）是文字格，不算。
- 區域成為一塊，上限是切塊大小的 3 倍（1,200 tokens）；超過時依列切開，每一段都重複標題與表頭。前後的內文照原本的固定長度切塊。
- 結果：論文切成 46 塊（原 48）。Table 2 是第 8 頁的 #22，941 tokens，22 行全在；Table 1（第 7 頁）同樣成為一塊，943 tokens。其餘 44 塊都在 400 tokens 以內。
- 代價：這兩塊比一般切塊大 2.4 倍，各佔檢索結果的一個名額，但證據量仍遠低於預算（941 ＋ 4 × 400 ＝ 2,541）。表格偵測是針對「pypdf 一列一行」的輸出寫的規則；其他解析器或版面要另外驗證。

## 基準（固定長度）的細節

論文切成 48 塊。Table 2 在第 8 頁，這一頁有 5 塊，表格落在前 3 塊：

| 切塊 | tokens | 開頭 | 結尾 |
|---|---|---|---|
| #24 | 400 | `Table 2: Performance of ablated versions…` | `…Empowerment 36.0% 64.` |
| #25 | 400 | `76.4% 40.4% 59.6%`（一列的後半） | `…NaiveRAG -Origin` |
| #26 | 400 | `% 16.4% 83.6% 35.2% 64.8%`（一列的後半） | 表格之後的內文 |
| #27 | 400 | 內文 | 內文 |
| #28 | 266 | 內文 | 內文 |

表格的 16 列（4 個區塊 × 4 個指標）：

| 檢查 | 結果 |
|---|---|
| 整列完整出現在至少一個切塊中 | 16/16 |
| 整列與它的區塊標題（如 `NaiveRAG -High` × 4）在同一個切塊 | 14/16 |
| 整列與資料集標題（`Agriculture CS Legal Mix`）在同一個切塊 | 6/16 |

## 具體的問題

- **資料集標題只出現在 #24。** #25 與 #26 裡的列有完整的 8 個數值，但看不出哪一欄是哪個資料集。只檢索到這兩塊時，數字與資料集對不起來。
- **`-High` 區塊被切成兩半。** 它的標題與前兩列在 #24，`Empowerment` 與 `Overall` 兩列在 #25，而 #25 裡沒有 `-High` 的標題。這兩列會被誤以為屬於別的區塊。
- **列從中間被切開。** #24 結尾是 `Empowerment 36.0% 64.`，#25 開頭是 `76.4% 40.4% 59.6%`。重疊的 80 tokens 讓這幾列在相鄰的切塊中各有一份完整的，所以 16 列都至少完整一次。

## 之後怎麼用

P3 採用表格區域獨立成塊後三項皆 16/16；AC-14 的最終判定以真實模型回答 Q3 並對照 `../ground-truth/key-facts.md` 為準。P4 的切塊實驗（256／400／600）沿用這個做法，表格塊的上限隨切塊大小變動（3 倍）。

## UC-00 註冊、登入、登出

**使用者的動作**

1. 開啟網站，進入註冊頁，輸入使用者名稱與密碼。`POST /auth/register`
2. 在登入頁輸入同一組帳密。`POST /auth/login`
3. 使用一段時間後按登出。`POST /auth/logout`

**系統預期的反應**

1. 註冊：檢查 `Origin`；檢查使用者名稱是否已被使用；密碼以 Argon2 雜湊後儲存，不存明文。註冊不自動登入。
2. 登入：比對密碼。成功時產生全新的 Session token，資料庫只存它的雜湊；以 `HttpOnly`、`SameSite=Lax` 的 Cookie 回傳。請求若帶著舊的 Session，先刪除再發新的。
3. 之後的每個請求由瀏覽器自動帶上 Cookie；後端由 Session 找出使用者，作為每個操作的「操作者」。
4. 登出：刪除伺服器端的 Session 並清除 Cookie。

**預期的結果**

- 登入後畫面顯示自己的名稱，可以進入文件與對話頁面。
- 登出後回到登入頁；用舊的 Cookie 再呼叫任何需要登入的 API 都回 `401`。
- 帳號不存在與密碼錯誤顯示相同的訊息。

**不應發生的事**

- 資料庫或日誌中出現明文密碼。
- 未登入可以看到任何文件或對話。
- 來自其他網站的請求能以使用者的身分改變資料。

**對應**：AC-28、AC-29、AC-30、AC-31、AC-44、AC-45

## UC-01 上傳論文

**使用者的動作**

把 `2410.05779v3.pdf`（LightRAG 論文，16 頁）拖進上傳區。`POST /documents`

**系統預期的反應**

1. 檢查副檔名與大小；計算內容雜湊，確認自己沒有上傳過相同內容。
2. 存檔，建立文件（`uploaded`）與一筆 `index` 工作（`queued`），立刻回應 `202`。前端以 `GET /documents/{id}/events` 接收進度。
3. 工作開始，文件變 `processing`。解析：用本地程式庫逐頁取出文字並保留頁碼，不把檔案交給任何 LLM。
4. 切塊：每頁依 token 數切成 400 一塊、重疊 80。全文約 14,443 tokens，逐頁切塊後預期約 45–50 塊。
5. 嵌入：分批送 `bge-m3`，整篇約 1–2 秒。
6. 所有切塊與「文件變 `ready`」在同一個交易內寫入。此時已經可以提問。
7. 自動排入 `summary` 工作（P3），摘要狀態變 `processing`：辨識章節 → 每章節摘要 → 合併成全文摘要。每次呼叫都先過預算檢查並寫入帳本。預估 2–4 分鐘。完成後摘要狀態變 `ready`。

**預期的結果**

文件清單出現這份檔案，顯示目前的階段與進度；切塊完成後即可勾選來提問，摘要的進度另外顯示（例：摘要 3／9）。重新整理頁面後進度仍在。

**不應發生的事**

- 上傳後畫面沒有任何進度。
- 入庫失敗卻顯示為可用，或留下一半的切塊。
- 必須等摘要做完才能提問。

**對應**：AC-01、AC-03、AC-11

## UC-02 問題 1：摘要全文

**使用者的動作**

建立對話，選取論文，輸入 `summary this document.`
`POST /conversations`，接著 `POST /conversations/{id}/messages`

**系統預期的反應**

1. 確認對話與文件都屬於操作者，文件已 `ready`。建立使用者訊息與助理訊息（`pending`）。
2. 判斷問題類型：命中關鍵字 `summary`，判定為摘要類。
3. 確認這份文件的摘要狀態為 `ready`。
4. **不做向量檢索**。整篇論文 14,443 tokens 放不進 10K，所以用入庫時存好的全文摘要與章節摘要當作證據。
5. 組 prompt：系統指示＋問題＋摘要。送出前計數，確認加上輸出保留量後不超過 10,000。
6. 助理訊息變 `streaming`，串流生成。來源標示為各章節的摘要，帶章節標題與頁碼範圍。
7. 回答完成後，檢查其中的數字是否出現在所引用頁面的原文；找不到的列在回答後。
8. 助理訊息變 `completed`；帳本新增一筆 `answer`，關聯到這則訊息。

**預期的回答**

- 涵蓋三件事：論文要解決的問題、提出的方法、主要的實驗結果。（具體要點待建立）
- 來源列出章節與頁碼範圍，可點開。
- 提問當下只呼叫一次 LLM；摘要的運算在入庫時已經做完。

**不應發生的事**

- 只摘要了論文的前半部（代表內容被截斷）。
- 帳本出現超過 10,000 tokens 的紀錄。

**對應**：AC-12、AC-17、AC-26

## UC-03 問題 2：比較 LightRAG 與 GraphRAG

**使用者的動作**

輸入 `compare lightRAG with GraphRAG`

**系統預期的反應**

1. 沒有摘要關鍵字，判定為一般檢索。
2. 把問題嵌入成向量，在操作者自己、且這次選取的文件中取相似度最高的 5 段。
3. 第一名的相似度預期高於門檻 0.45（先前的小實驗中，類似問題約 0.66），繼續往下。
4. 把 5 段（最多約 2,000 tokens）連同檔名與頁碼裝進 prompt；指示 LLM 只依這些片段作答、每個論點標註來源編號、證據不足要明說。
5. 送出前計數：約 500（指示）＋200（問題）＋2,000（證據）＝約 2,700，加上輸出保留 2,500，遠低於 10,000。
6. 串流生成；回答結束後把來源編號對應回檔名、頁碼與原文片段，連同訊息一起保存。

**預期的回答**

- 同時談到 LightRAG 與 GraphRAG，並至少提出兩項論文中寫到的具體差異。（差異要點待建立）
- 每個論點後面有來源編號，點開能看到該頁的原文片段。

**已知風險**

比較的依據散在論文多個段落。只取 5 段有可能漏掉部分面向。這一題是否答得完整，是 P4 比較 Top-K 3／5／8 時的重點觀察對象。

**不應發生的事**

- 引用了 5 段以外的內容，或寫出論文沒有的比較。

**對應**：AC-04、AC-05、AC-13

## UC-04 問題 3：消融版本的表現

**使用者的動作**

輸入 `Performance of ablated versions of LightRAG`

**系統預期的反應**

1. 判定為一般檢索，取前 5 段。
2. 答案主要在論文的 Table 2 與 4.3 節的文字說明。Table 2 約 1,000 tokens，固定長度切塊會把它切成約三塊。
3. 這三塊是否都被取回、LLM 能否從被切開的表格讀出正確數字，是這一題的關鍵。**這一題必須在 P3 通過**；固定切塊答不對時，P3 內就要修正（做法見 `02-architecture.md` 第 5 節）。

**預期的回答**

- 說明三種消融版本（`-High`、`-Low`、`-Origin`）相對於完整 LightRAG 的表現變化。（各版本代表移除什麼，待依 4.3 節原文建立）
- 引用的數字必須與 Table 2 一致。以「Overall」一列、對 NaiveRAG 的勝率為例：

  | 資料集 | LightRAG | -High | -Low | -Origin |
  |---|---|---|---|---|
  | Agriculture | 67.6% | 64.8% | 65.2% | 74.4% |
  | CS | 61.2% | 56.0% | 56.4% | 60.8% |
  | Legal | 84.8% | 78.0% | 81.2% | 84.4% |
  | Mix | 60.0% | 57.6% | 64.8% | 55.6% |

  （以上數字取自論文 Table 2 的文字抽取結果，P3 建立關鍵事實清單時再與 PDF 原頁逐格核對。）

- 來源指向 Table 2 所在的頁面。

**不應發生的事**

- 數字張冠李戴（把某個資料集或版本的數字寫到另一個）。
- 只描述趨勢而沒有任何數字，或寫出表格中不存在的數字。

**對應**：AC-14

## UC-05 追問（對話記憶）

**使用者的動作**

在同一個對話中，接在 UC-03 之後輸入 `那它的缺點呢？`

**系統預期的反應**

1. 這句話單獨看不知道「它」指什麼。先用一次 LLM 呼叫，依這個對話先前的訊息把問題改寫成完整的問題。帳本記為 `rewrite`。
2. 用改寫後的問題做檢索與回答，流程同 UC-03。
3. 對話記憶有上限（約 800 tokens）：保留最近幾輪原文，更早的只留摘要。狀態不是 `completed` 的助理訊息不納入記憶。

**預期的回答**

- 回答的主題與上一題一致，沒有答非所問。
- 若論文沒有明確討論缺點或限制，回答要說明文件中沒有相關內容，不自行推論。

**不應發生的事**

- 把「它」當成字面去檢索，取回不相關的片段。
- 對話越長、prompt 越大，最後超過 10,000。

**對應**：AC-16、AC-17

## UC-06 文件裡沒有答案的問題

**使用者的動作**

輸入 `如何在家烤酸種麵包？`

**系統預期的反應**

1. 判定為一般檢索，取前 5 段。固定 Top-K 一定會回傳 5 段，即使都不相關。
2. **第一道防線**：第一名的相似度低於門檻 0.45（小實驗中，無關問題最高約 0.33）。直接回覆找不到，不呼叫 LLM，帳本不新增紀錄。
3. **第二道防線**（相似度剛好過門檻時）：LLM 被指示證據不足要明說；回答中沒有任何來源標註時，視為找不到答案。

**預期的回答**

固定的說明文字，例如「在選取的文件中找不到與這個問題相關的內容」。助理訊息為 `completed`、`answered` 為 `false`，不附來源。

**不應發生的事**

- 用模型自己的知識回答麵包怎麼烤。
- 硬湊論文內容來回答。

**對應**：AC-15

## UC-07 多份文件：限定範圍與跨文件提問

**前置**：已上傳 LightRAG 論文。

**使用者的動作**

1. 再上傳 GraphRAG 論文（arXiv 2404.16130）。
2. 只勾選 GraphRAG 論文，問一個只有該文件能回答的問題。
3. 兩份都勾選，問 `這兩篇論文各自怎麼描述 GraphRAG 的檢索成本？`
4. 不勾選任何文件，直接提問。

**系統預期的反應**

- 步驟 2：檢索只在勾選的文件內進行，來源全部來自 GraphRAG 論文。
- 步驟 3：在兩份文件的所有切塊中取前 5 段。K 是兩份文件合計，不保證每份都有。來源標示各自的檔名與頁碼。
- 步驟 4：搜尋範圍是自己所有已就緒的文件，跨文件共用 Top-K = 5。介面明確顯示搜尋範圍為「所有可用文件」，讓使用者知道系統正在搜尋哪些文件。

**預期的回答**

- 步驟 2：來源只有 GraphRAG 論文。
- 步驟 3：分別說明兩篇各自的描述，並標明哪句話出自哪一篇。若 5 段全部來自同一篇，回答要說明另一篇沒有取得相關內容，不自行補充。

**已知風險**

固定 Top-K 可能只取到其中一篇。這是 P4 跨文件題要量測的項目；「每份文件保底名額」是選做的對照實驗。

**不應發生的事**

- 步驟 2 的來源出現沒有勾選的文件。
- 把 A 論文的說法標成 B 論文。

**對應**：AC-06、AC-48

## UC-09 錯誤情境

| 情境 | 使用者的動作 | 系統預期的反應 |
|---|---|---|
| 不支援的格式 | 上傳 `.docx` | 回 `415` 與說明，不建立文件紀錄 |
| 空檔 | 上傳空白的 `.txt` | 回 `422`，不建立文件紀錄 |
| 抽不出文字 | 上傳掃描版 PDF | 上傳被接受；`index` 工作失敗，文件變 `failed`，原因為沒有可讀取的文字 |
| 重複上傳 | 同一份論文再傳一次 | 回 `200` 與既有的文件，不重複入庫 |
| 尚無可用文件就提問 | 文件還在處理中時送出問題 | 回 `409`，不呼叫 LLM，不建立訊息 |
| 提問時 LLM 無法連線 | Ollama 停止服務 | 串流送出 `error`；助理訊息變 `failed`；帳本該筆記為 `failed`，實測值未知 |
| 回答到一半離開 | 串流途中關閉分頁 | 後端停止生成；助理訊息變 `interrupted` 並保留已產生的文字；帳本該筆記為 `interrupted`，實測值未知，另記已收到文字的預估計數 |
| Session 過期 | 放置超過有效期後操作 | 回 `401`，前端導向登入頁 |

**對應**：AC-02、AC-08、AC-22、AC-41

## UC-10 超量保護

**使用者的動作**

貼上一段很長的文字當作問題（數千字），或在很長的對話之後繼續追問。

**系統預期的反應**

1. 問題本身超過問題的預算（`QUESTION_TOKEN_BUDGET`，預設 200 tokens）時，回 `422` 並提示使用者縮短問題。不送給 LLM、不建立訊息，也不截斷問題〔使用者決定，D45〕。
2. 對話記憶超過上限時，把較早的內容濃縮，維持在上限內。
3. 任何情況下，組好的 prompt 加上輸出保留量若超過 10,000，在送出前被擋下並回報錯誤，不會交給 Ollama 默默截斷。

**不應發生的事**

- 帳本出現實測總和超過 10,000 的紀錄。
- 回答看起來正常，但其實證據被截掉一部分。

**對應**：AC-07、AC-08、AC-49

## UC-11 刪除文件

## UC-12 跨使用者的資料隔離

**前置**：使用者 A 與 B 各自登入，各自上傳了文件並有對話。

**使用者的動作**

B 以自己的身分，嘗試用 A 的文件 id 與對話 id 呼叫各個 API；或在提問時把 A 的文件 id 放進 `document_ids`。

**系統預期的反應**

- 讀取、刪除、重試、接收進度、讀取對話、刪除對話：一律回 `404`，如同該資源不存在。A 的資料不變。
- 提問時指定 A 的文件：回 `404`，不檢索、不呼叫 LLM。
- B 的文件清單、對話清單、LLM 呼叫帳本只有自己的資料。
- A 與 B 上傳內容完全相同的檔案時，各自擁有自己的文件、切塊與檔案；B 不會因為內容相同而取得 A 的文件。

**不應發生的事**

- 回 `403` 而讓人得知該資源存在。
- 任何回答的來源出現別人的文件。

**對應**：AC-32、AC-33、AC-34、AC-35

## UC-13 入庫失敗與重試

**使用者的動作**

上傳文件時，嵌入服務剛好無法連線。稍後服務恢復，使用者按下重試。`POST /documents/{id}/retry`

**系統預期的反應**

1. `index` 工作在嵌入階段失敗：整批寫入復原，沒有任何切塊留下；工作與文件都標為 `failed`，記錄原因。
2. 重試：建立一筆新的 `index` 工作，重試次數為 1；舊的工作紀錄保留。
3. 這次成功：在同一個交易內先清除既有的切塊再寫入新的，文件變 `ready`。

**預期的結果**

文件顯示失敗與原因，並有重試按鈕；重試成功後變為就緒。文件不需要刪除重傳。

**不應發生的事**

- 失敗後留下部分切塊，使文件「半可用」。
- 重試後出現重複的切塊。
- 對處理中或已就緒的文件可以按重試。

**對應**：AC-36、AC-37

## UC-14 摘要尚未完成或失敗時提問

**前置**：文件已 `ready`，摘要狀態為 `processing` 或 `failed`。

**使用者的動作**

1. 問一般問題，例如 `compare lightRAG with GraphRAG`。
2. 問 `summary this document.`

**系統預期的反應**

- 步驟 1：正常檢索與回答，不受摘要狀態影響。
- 步驟 2：判定為摘要類，但摘要不可用。回覆「摘要仍在產生中，請稍後再試」或「摘要產生失敗，可在文件清單重試」，`answered` 為 `false`，不呼叫 LLM。不改用檢索硬湊一份摘要。

**預期的結果**

文件清單分別顯示文件狀態與摘要狀態。摘要失敗時可以單獨重試摘要，不需要重新建索引。

**對應**：AC-42

## UC-15 刪除處理中的文件

**使用者的動作**

上傳一份大文件，在它還在嵌入或摘要時按下刪除。

**系統預期的反應**

1. 刪除的交易移除文件與它的工作紀錄、切塊、摘要。
2. 背景工作在下一次寫入前確認自己的工作紀錄：已經不存在，立刻放棄，不寫入任何資料。
3. 進行中的 LLM 呼叫若被取消，帳本記為 `interrupted`，實測值未知。
4. 原始檔案在資料庫交易成功後刪除。

**預期的結果**

文件立刻從清單消失，之後也不會再出現任何屬於它的切塊或摘要。

**不應發生的事**

- 刪除後背景工作繼續寫入，留下沒有文件的切塊或摘要。
- 刪除的請求要等整個處理跑完才回應。

**對應**：AC-38、AC-46

## UC-16 服務重啟

**情境**

文件處理到一半、或回答串流到一半時，後端程序被重新啟動。

**系統預期的反應**

後端啟動時：

- 排隊中或執行中的處理工作標為 `failed`，原因為服務重啟；對應的文件狀態或摘要狀態標為 `failed`。
- 產生到一半的助理訊息標為 `interrupted`。
- 尚未結束的 LLM 呼叫紀錄標為 `failed`，實測值未知。

**預期的結果**

使用者重新整理後，看到文件為失敗並可重試；未完成的回答標示為未完成。沒有任何物件永遠卡在「處理中」。

**不應發生的事**

- 文件永遠顯示處理中。
- 半截的回答顯示為完整回答。

**對應**：AC-39、AC-50

## UC-17 對話紀錄的保存與刪除

**使用者的動作**

1. 登出後重新登入，開啟對話清單，點選先前的對話。`GET /conversations`、`GET /conversations/{id}`
2. 刪除其中一段對話。`DELETE /conversations/{id}`

**系統預期的反應**

- 清單只列出自己的對話，依最後更新時間排序。
- 讀取對話時回傳所有訊息，以及每則回答當時保存的來源（檔名、頁碼、片段）。即使來源文件之後被刪除，舊對話仍能顯示當時的來源。
- 狀態不是 `completed` 的助理訊息標示為未完成。
- 刪除對話時訊息一併刪除；LLM 呼叫紀錄保留，不再指向這段對話。

**不應發生的事**

- 重新登入後對話消失。
- 清單出現別人的對話。

**對應**：AC-33、AC-40

## UC-18 個人偏好

**使用者的動作**

在個人資料頁把回答語言設為繁體中文、詳細程度設為簡短，然後提問。`PATCH /users/me`

**系統預期的反應**

- 設定保存在使用者資料上。
- 之後的提問，在給 LLM 的指示中加入回答語言與詳細程度。
- 偏好只影響回答的寫法，不影響檢索、引用、拒答與 10K 的規則；「詳細」也不會讓輸出超過輸出保留量。

**預期的結果**

新的回答以繁體中文、較短的篇幅呈現，仍然附來源。

**對應**：AC-43

狀態：已確認（2026-11-05，決策日誌 D46）。P1 完成後凍結；之後只在實作或測試發現實際問題時修改，並記入決策日誌。
相關：`02-architecture.md`（怎麼做）、`03-interfaces.md`（API、物件、資料表）、`04-use-cases.md`（使用情境劇本）。

## 1. 要做什麼

DocuMind-AI 是一個本地執行的 AI 文件管理與問答平台。使用者註冊登入後，管理自己上傳的文件，用聊天介面對指定的文件提問，LLM 依文件內容回答並附上來源。

最核心的功能仍然是能可靠回答文件問題的 RAG 系統。平台功能不能犧牲題目原本的驗收條件。

目標是「架構合理、資料生命週期完整、真正具備 RAG 能力，而且可以向審閱者展示與解釋的 AI-Native 文件平台」，不是最複雜的平台。

**里程碑**（以 2026-11-05 為第 1 天）

- 第 4 天結束：完成「登入 → 上傳 → 提問 → 附來源的回答」。
- 第 5 天結束：三個指定問題通過。

里程碑是目標。**不得為了趕時間而跳過必要的驗收。** 進度落後時依下方的順序調整範圍。

**範圍調整的順序**

1. 個人偏好（F-13）。
2. 修改個人資料。
3. Document-aware Retrieval 對照實驗（本來就是選做）。
4. 縮小 P4 的實驗規模：減少組合數與回答正確性的測試題數。
5. 重試與對話刪除的介面按鈕（保留 API）。

Hybrid Search 的實驗已列入 AC-19，不直接取消；時間不足時先縮小規模。任何已列入驗收條件的項目若要取消，**必須先修改驗收條件並在決策日誌記錄原因**。

不調整的必要項目：三個指定問題、引用、10K 限制、登入與資料隔離。

## 5. 驗收條件

每條都要能實際執行並判定。狀態在各階段回顧中標 PASS／FAIL／NOT TESTED。編號依加入的先後，不代表順序。

### P2-A 帳號與骨架

| 編號 | 驗收條件 | 驗證方式 |
|---|---|---|
| AC-27 | 所有 API 位於 `/api/v1`；查詢用 GET、建立與動作用 POST、修改用 PATCH、刪除用 DELETE；GET 不改變資料；API 文件頁（`/api/v1/docs`）可開啟 | 自動測試檢查路由表 |
| AC-28 | 註冊成功後可用同一組帳密登入；重複的使用者名稱回 `409` | 整合測試 |
| AC-29 | 資料庫中的密碼欄位不是明文；兩個帳號用相同密碼，雜湊值不同 | 整合測試＋查資料庫 |
| AC-30 | 未登入時呼叫任何需要登入的端點都回 `401`（逐一檢查路由表，只排除註冊、登入、健康檢查與 API 文件頁；測試請求帶允許的 `Origin`） | 自動測試 |
| AC-31 | 登出後，原本的 Session 再呼叫回 `401` | 整合測試 |
| AC-44 | 會改變資料的請求（POST、PATCH、DELETE）依以下規則驗證來源，與 `02-architecture.md` 第 2.4 節一致：有 `Origin` 時，它必須在允許清單內；沒有 `Origin` 時改看 `Referer` 的來源，必須在允許清單內；兩者都不存在、或來源不在清單內，回 `403` 且資料不變。來源合法的請求（含只有合法 `Referer` 的）正常處理 | 整合測試（五種情況：合法 Origin、不合法 Origin、無 Origin 但 Referer 合法、無 Origin 且 Referer 不合法、兩者皆無） |
| AC-45 | 登入後的 Session 與登入前帶來的任何 Cookie 值不同；登入前的舊值無法通過驗證 | 整合測試 |
| AC-47 | 最小流程驗證腳本通過：以 `bge-m3` 嵌入數段文字 → 寫入 pgvector → 以相似度取回 → 交給 `qwen3:32b` 產生回答，並印出 Ollama 回報的 token 數 | 執行腳本 |

| 編號 | 驗收條件 | 驗證方式 |
|---|---|---|
| AC-02 | 上傳不支援的格式（如 `.docx`）回傳明確的錯誤訊息，不建立文件紀錄 | 整合測試 |
| AC-35 | 使用者 A 與 B 上傳內容相同的檔案，各自得到自己的文件；A 重複上傳得到既有文件 | 整合測試 |

### P2-C 入庫

| 編號 | 驗收條件 | 驗證方式 |
|---|---|---|
| AC-01 | 登入後上傳 PDF、TXT、Markdown 各一份，都入庫成功並出現在文件清單 | 手動＋整合測試 |
| AC-03 | 論文入庫後，每個切塊的 token 數都不超過設定的切塊大小，且每塊都記有文件與頁碼 | 單元測試＋查資料庫 |
| AC-25 | 本地 tokenizer 的計數與 Ollama 回報的 `prompt_eval_count` 比對，涵蓋中文、英文、中英混合、程式碼、多輪對話五種情境，每種各測短、中、接近上限三種長度。**不允許低估**：每一筆都必須滿足「本地計數＋安全緩衝 ≥ Ollama 實測值」；高估不得超過 32 tokens 與實測值 2% 兩者中較大者。這一條只驗收本地計數的準確度，不代表伺服器端的防護（見 AC-55、AC-56） | 標記為 `llm` 的測試 |
| AC-54 | 每一個 LLM 生成請求都帶齊並放對位置：`options.num_ctx` 等於 context 上限、`options.num_predict` 為這次呼叫的輸出上限（大於 0 且小於 context 上限）、最上層的 `truncate` 與 `shift` 皆為 `false`。請求只在一處組裝，其他程式（含驗證腳本）不得自行組裝 | 單元測試 |
| AC-55 | 伺服器端拒絕超量輸入：輸入超過 context 上限時，Ollama 回 HTTP 400、不產生任何內容、不截斷；接近上限但放得下的輸入完整被處理。串流與非串流皆同 | 標記為 `llm` 的測試 |
| AC-56 | 伺服器端不捨棄已有的內容、輸出不超過上限：prompt 接近 context 上限時，輸出在 context 用盡時停止，prompt＋輸出不超過上限；輸出不超過 `num_predict`。自然結束、達到輸出上限、context 用盡三種停止原因可以由回應區分 | 標記為 `llm` 的測試 |
| AC-32 | 使用者 A 對使用者 B 的文件做讀取、刪除、重試、進度串流，皆回 `404`，B 的資料不變 | 整合測試 |
| AC-36 | 入庫失敗（模擬嵌入服務錯誤）：文件為 `failed` 並有原因，切塊數為 0，處理工作為 `failed` | 整合測試 |
| AC-37 | 對 `failed` 的文件重試後變為 `ready`；切塊沒有重複；處理工作有兩筆，重試次數遞增 | 整合測試 |
| AC-38 | 刪除文件後，它的切塊、摘要、處理工作與原始檔案都不存在；相關的 LLM 呼叫紀錄仍在，文件欄位為空（摘要自 P3 起納入測試） | 整合測試 |
| AC-39 | 服務啟動時，處於 `queued`／`running` 的處理工作被標為 `failed`，文件可重試 | 整合測試 |
| AC-46 | 刪除處理中的文件：刪除後背景工作不再寫入任何切塊或摘要；工作結束後資料庫中仍沒有該文件的任何資料（摘要自 P3 起納入測試） | 整合測試（在工作中插入延遲） |

### P2-D 問答

| 編號 | 驗收條件 | 驗證方式 |
|---|---|---|
| AC-04 | 對論文提問，回答以串流逐步出現 | 手動 |
| AC-05 | 回答附至少一筆來源，含檔名、頁碼、片段；片段文字確實出現在該文件的該頁 | 整合測試 |
| AC-06 | 有兩份文件時，只選其中一份提問，檢索結果不含另一份的內容 | 整合測試 |
| AC-07 | 組裝出的 prompt 加上輸出保留量超過 10,000 tokens 時，呼叫在送出前被擋下並拋出明確錯誤 | 單元測試 |
| AC-08 | 每次 LLM 呼叫都寫入帳本，包含失敗、被 Ollama 拒絕（輸入超量）與串流中斷的呼叫。每筆記錄狀態、送出前的預估 prompt tokens 與輸出上限（合稱預算上界），以及 Ollama 回報的實測值。**拿不到實測值時，實測欄位留空並標示為未知。** 合規報告分開列出：有實測值的呼叫數與其中最大的實測總和；沒有實測值的呼叫數與其預算上界。兩者皆 ≤ 10,000，且報告不把後者稱為實測合規。帳本只回傳自己的紀錄 | 單元測試（模擬失敗與中斷）＋查帳本 API |
| AC-09 | 程式碼沒有任何雲端 LLM 或文件解析服務的相依；LLM 介面只接受與回傳文字 | 檢視相依清單＋型別檢查 |
| AC-10 | `docker compose up --build` 後，在瀏覽器完成「註冊並登入 → 上傳論文 → 提問 → 看到附來源的回答」 | 手動 |
| AC-33 | 使用者 A 無法讀取、刪除 B 的對話，也無法在 B 的對話中提問（皆回 `404`）；A 的帳本查不到 B 的呼叫 | 整合測試 |
| AC-34 | A 與 B 各有文件。A 提問時，檢索結果與來源不含 B 的文件；A 在請求中指定 B 的文件 id 時回 `404` | 整合測試 |
| AC-40 | 對話與訊息在重新登入後仍可讀取；刪除對話後訊息一併刪除，LLM 呼叫紀錄保留 | 整合測試 |
| AC-41 | 串流中斷（模擬用戶端斷線）：助理訊息的狀態為 `interrupted`，不是 `completed` | 整合測試 |
| AC-48 | 提問時沒有指定任何文件：檢索範圍為自己所有 `ready` 的文件，跨文件共用同一個 Top-K；回應中標明實際的搜尋範圍，介面顯示為「所有可用文件」 | 整合測試＋手動 |
| AC-49 | 問題的 token 數超過 `QUESTION_TOKEN_BUDGET`（預設 200）時回 `422`、`code` 為 `QUESTION_TOO_LONG`，不呼叫 LLM、不建立訊息、不截斷問題；調整設定值後，判定隨之改變 | 單元測試＋整合測試 |
| AC-50 | 服務啟動時，`pending`／`streaming` 的助理訊息標為 `interrupted`，`pending` 的 LLM 呼叫標為 `failed` 且實測欄位為空 | 整合測試 |
| AC-57 | 回答未完整生成時不標為完成：停止原因不是自然結束（達到輸出上限、context 用盡或無法判定）時，助理訊息的狀態為 `interrupted`、不是 `completed`，已產生的內容保留；帳本記錄該次呼叫的停止原因與實測值，且能區分達到輸出上限、context 用盡與使用者中斷連線。被 Ollama 拒絕的呼叫在帳本為 `failed`、實測欄位為空，助理訊息為 `failed` | 整合測試（模擬各種停止原因） |

## 目標

1. 以兩個小實驗取得 token 與 embedding 的實測數據。
2. 寫出可驗收的規格，並經使用者確認。
3. 規格確認後凍結主要架構，作為 P2 的依據。

## 做了什麼

- **兩個實驗**（結果在 `../02-specs/02-architecture.md` 第 1 節）：

  - `bge-m3`：1024 維；30 段一批 1.39 秒；中文問題可找到正確的英文段落；無關問題的最高相似度 0.33。

- **專案定位改為平台**：使用者系統、文件與對話管理、資料隔離、處理工作、RESTful API；RAG 的技術決策全部保留。

- **checkpoint skill 改版**：採用使用者帶來的建議，加上 `references/` 與檢查腳本。

## 與 AI 的協作方式

- 順序是先實驗、再寫規格。規格草稿由 AI 寫，切塊、檢索、摘要三個部分由使用者先定方向。
- 規格經過四輪審閱與修訂才確認：六項修正 → 平台化重新規劃 → 十一項取捨與四項技術要求 → 五項待決事項與三個驗收條件的細節。
- AI 做得好的地方：
  - 用實測數據支持設計（例如證明必須在送出前自行擋下超量）。
  - 指出使用者選擇的後果（固定 Top-K 無法拒答、固定長度會切開 Table 2），讓使用者接著補上對應的決定。
  - 整合時找出規格之間的衝突（`cancelled` 狀態與刪除規則互斥）與缺口（服務重啟後訊息的處理沒有驗收條件）。
  - 被要求「不要照單全收」時，提出成本估計、風險與刪減順序。
- AI 需要修正的地方：
  - 建議不做登入與使用者；使用者決定做成平台。
  - 把 Hybrid 實驗列為可直接刪減，忽略它已在驗收條件內。
  - 把 SameSite 加 JSON 請求當成 CSRF 防護。
  - 把「通過送出前的預算檢查」說成不影響合規判定，混淆預估與實測。
  - 把里程碑稱為「硬性的」時間線。
  - 刪除文件與背景工作的互動只寫了一句「標為 cancelled」，沒有設計失效機制。

## 困難與解法

| 現象 | 根因 | 嘗試過 | 解法 | 學到 |
|---|---|---|---|---|

| 規格經多輪修訂後變得雜亂 | 每一輪都在原檔上疊加標記、提案與歷史說明 | — | 現行規格只留四份並去掉過程標記；提案與原始計畫移到 `archive/`；決策過程集中在決策日誌 | 規格寫「現在是什麼」，過程寫在決策日誌 |

## 我的想法

以下是使用者在 checkpoint 時的回答，原文貼入。

**最不認同 AI 的哪個建議？為什麼？**

勾選：不做登入與使用者、把 Hybrid 列為可直接刪減、只靠 SameSite 當 CSRF 防護、把預估合規說成不失真。

> 我最不認同的是一開始建議不做登入與使用者管理。雖然這次作業的核心是 RAG，但我希望做出來的不只是能上傳文件、呼叫 LLM 的 Demo，而是一個有完整資料管理能力的平台。因此我認為應該先把 User、Document、Conversation 等基本物件，以及它們之間的關聯、權限與生命週期定義清楚，再逐步整合 RAG 功能。而且像 CSRF 防護、Token 用量這些會影響安全性與結果可信度的部分，也需要有實際的驗證依據，不能只停留在假設。

**哪些地方是你介入後才解決或變得更好的？當時怎麼判斷？**

勾選：Table 2 必須在 P3 通過、刪除文件時背景工作要失效、提早驗證最小流程。

> 我主要考慮的是核心功能是否真的能完成，以及整個系統的開發順序是否合理。首先，Table 2 是題目指定要回答的內容，所以我認為這不能只是後續的優化項目，而是必須在主要功能開發階段就確保能正確回答。另外，因為我希望這個專案不只是 RAG Demo，而是一個具有完整資料管理能力的平台，所以特別重視物件的生命週期。例如使用者刪除文件時，如果背景工作還在執行，就可能發生資料被刪除後又重新寫入的問題，因此需要在架構階段先考慮。最後，我認為不應該等到前後端全部完成後才整合 AI 功能。如果能先透過最小流程驗證 Ollama、Embedding 和資料庫之間的運作，就可以提早發現問題，降低後續整合的風險。

**對自己的做法有什麼感想？對 P2 最在意什麼？**

勾選：方向改了幾次、先規劃再實作的價值、對 P2 的擔心。

> 我覺得 P1 最大的收穫，是發現自己一開始對專案的想法還沒有那麼完整。原本主要是想完成題目要求的 RAG 功能，但在跟 AI 討論架構的過程中，我開始思考，如果未來要持續擴充，應該要怎麼管理使用者、文件、對話紀錄，以及這些物件的生命週期，所以才決定把它往平台的方向設計。這其實也跟我過去接觸平台開發與系統維護的經驗有關。以前在處理系統功能和資料庫時，就有體會到如果一開始沒有把資料結構、物件之間的關聯，以及各個功能的責任劃分清楚，後續要新增功能或修改既有邏輯時，可能就需要花更多時間調整。因此這次即使只是短期的 Assignment，我還是希望先建立一個比較完整、合理的系統骨架，而不只是讓功能可以跑起來就好。雖然中間有幾次調整，例如 API 的設計方式，但我覺得在實作前發現問題並修改，比寫完程式後才重新調整好很多。今天確實花了不少時間在討論規格，還沒真正開始開發功能，但至少現在對每個階段要做什麼、為什麼這樣設計都有比較清楚的方向。我也發現 AI 可以很快提出架構與實作方案，但這些建議不一定完全符合我想做的系統，還是需要自己根據過去的經驗和專案需求去判斷與調整。接下來 P2 我最在意的是實際整合會不會遇到預期外的問題，尤其是資料庫、前後端與 LLM 之間的串接。另外，因為增加了登入與平台管理功能，也擔心花太多時間在骨架上，反而壓縮到 RAG 核心功能的開發。因此希望先完成基本架構，再盡早驗證整個問答流程，而不是等所有功能都做好才開始整合。

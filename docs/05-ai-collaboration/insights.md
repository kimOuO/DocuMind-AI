- 2026-11-05｜**自動化測試與人工驗收具有互補性**：在前端功能驗收時，發現刪除確認視窗的標題受到瀏覽器原生行為影響，而元件測試使用模擬實作，因此未能呈現實際操作情況。這讓我體會到，自動化測試雖然能有效驗證功能邏輯，但無法完全取代真實瀏覽器中的使用者操作驗收。開發過程應同時考慮測試覆蓋率與實際使用體驗。｜decision-log D53
- 2026-11-05｜**技術選型應建立在客觀實驗與需求評估之上**：AI 在實作前指出 PyMuPDF 的 AGPL 授權限制，並提出繼續使用或更換套件的方案。我認為授權雖然重要，但不應成為唯一的決策依據，因此要求先比較不同 PDF 解析套件，並以論文段落完整性、表格數值正確性、版面解析能力及執行效能作為評估標準。最終選用 pypdf，同時確認其章節標題辨識存在限制。這次經驗讓我更加重視以可量測的實驗結果支持架構與技術選型，而非僅依賴 AI 的初步建議。｜decision-log D54；ADR 0005
- 2026-11-05｜**相同的設定與資料不代表相同的執行結果**：在 Tokenizer 驗證過程中，即使本地 Tokenizer 與 Ollama 使用相同的詞彙表及合併規則，實際 Token 計數仍存在差異。這說明系統行為除了取決於設定與資料，也可能受到底層演算法實作影響。因此，我認為在整合外部工具或模型時，除了確認版本與設定一致，更需要透過端到端測試驗證實際行為，避免將理論上的相容性直接視為實際上的一致性。｜decision-log D55、D56
- 2026-11-05｜**在增加系統複雜度前，應先確認既有工具是否提供原生解決方案**：面對 Token 計數差異造成的超量風險，AI 最初提出自行設計保守計數機制。我進一步要求比較其他專案的處理方式，並調查 Ollama 是否具備相關控制能力，最終發現可以利用其原生的 Context 限制機制避免超量後靜默截斷。這次經驗讓我理解，面對技術問題時，不應立即增加自訂邏輯，而應先評估現有工具的功能與限制，以降低系統複雜度及後續維護成本。｜decision-log D56；ADR 0006
- 2026-11-05｜**驗收條件應區分不同層次的正確性與保證**：Token Guard 的設計包含本地 Token 計數與推論伺服器的 Context 限制，兩者雖然共同服務於 10K Token 的需求，但驗證目的並不相同。前者著重計數準確度與預算配置，後者則負責防止超量輸入造成內容截斷。因此，我要求將兩者拆分為獨立的驗收條件，避免單一測試通過就被解讀為整體機制已經得到完整驗證。這也讓我更加理解需求、測試證據與系統保證之間需要有明確的對應關係。｜decision-log D56；AC-25、AC-54–57
- 2026-11-05｜**測試案例必須涵蓋實際使用情境，而非僅驗證 API 功能**：AI 原先的測試主要使用英文問題，並以 API 回應作為驗收依據。然而，在我實際透過瀏覽器使用中文提問時，發現回答語言與預期不一致，且 Markdown 格式未正確渲染。這反映出測試案例即使全部通過，也不代表使用者體驗已達到預期。對於包含 LLM 的應用系統，除了後端功能與資料正確性，也應將多語言輸出、前端渲染與真實互動流程納入驗收。｜decision-log D58
- 2026-11-05｜**AI 產生的分析與結論仍需透過可重現的實驗驗證**：在調整回答提示詞後，我注意到回答長度似乎出現變化，因此要求進一步確認實際修改內容與影響。後續檢查發現，原先比較的兩次提問內容並不相同，因此重新使用一致的問題與不同提示詞進行多次測試，以排除測試條件不一致造成的誤判。同時，也發現回答中存在將引用文獻的研究貢獻誤歸屬於當前論文的情況。這讓我更加重視控制實驗變因，以及對 LLM 生成內容進行事實與來源歸屬驗證，而不是僅根據回答的流暢度判斷品質。｜decision-log D58

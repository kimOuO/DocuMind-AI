# ADR 0005：PDF 解析採用 pypdf

- 狀態：已採用
- 日期：2026-11-05
- 對應決策日誌：D54

## 背景

題目規定文件解析只能用本地程式庫，不得交給 LLM 或雲端 API。規格原本指定 PyMuPDF。開始實作入庫前確認授權時發現，PyMuPDF 是 AGPL-3.0 或商業授權的雙授權：專案若公開散布，需要以 AGPL 相容的方式開源。

解析品質直接影響回答品質，尤其題目指定的第三題要用到論文的 Table 2，所以不能只因為授權就更換，也不能不評估授權就沿用。

## 考慮過的選項

數據來自 `evaluation/pdf-parser-comparison/`。標準答案取自論文的 LaTeX 原始檔，與受測套件無關。

| 項目 | PyMuPDF 2.1 | pypdf 6.21.4 | pdfplumber 0.11.10 |
|---|---|---|---|
| 授權 | AGPL-3.0 或商業授權 | BSD-3-Clause | MIT |
| 連同相依的安裝大小 | 283.4 MB | 4.2 MB | 58.9 MB |
| 內文段落找得到（LightRAG 論文，70 個） | 70 | 70 | 69 |
| 段落順序錯置 | 0 | 0 | 0 |
| Table 2 數值在正確的列與欄（128 格） | 128 | 128 | 128 |
| Table 2 一列一行（16 列） | 0 | 16 | 16 |
| 雙欄閱讀順序（BERT 論文，66 個段落） | 66 | 66 | 16 |
| 標題文字完整（22 個） | 22 | 0 | 7（調整參數後 22） |
| 16 頁的解析時間（中位數） | 48 ms | 488 ms | 1,722 ms |
| 表格偵測 API | 有，但 Table 2 的數值被拆開 | 無 | 有，以文字對齊偵測可還原 16/16 列 |

選擇的優先順序由使用者訂定：pypdf 能滿足要求就用 pypdf；不行再考慮 pdfplumber；兩者都不達標且 PyMuPDF 明顯更好時，才評估維持 PyMuPDF。正式專案只放一個解析器。

## 決定

採用 **pypdf 的預設模式**（`page.extract_text()`）。

- 內文、閱讀順序（單欄與雙欄）、頁碼都達標。
- Table 2 的 128 個數值都落在正確的列與欄位置，而且保留一列一行的結構。
- 授權是 BSD-3-Clause，沒有散布上的限制；純 Python，安裝大小最小。
- pdfplumber 在雙欄文件會把左右兩欄接在一起，不採用。
- PyMuPDF 勝在標題與速度，不足以抵過 AGPL 與 283 MB 的相依。

不使用 pypdf 的 `layout` 模式：它在 Table 2 只有 61/128 格位置正確，在雙欄文件只找回 13/66 個段落。

## 後果

- **標題被拆開**：論文的標題用小型大寫字，pypdf 抽出後會變成 `1 I NTRODUCTION`、`3 T HE LIGHT RAG A RCHITECTURE`。22 個標題的文字都不完整；編號、所在頁與內文不受影響。只處理「編號開頭、全大寫」的行可以還原 15 個，其餘 7 個（`LIGHT RAG`、`LLM S` 這類）無法由規則判斷。
  - 因此不假設解析後的標題是正確的。章節摘要（P3）實作之前，先完成標題辨識與正規化的測試（驗收條件 AC-53）。
  - 章節的邊界以編號與所在頁判定，不依賴標題文字。
- **沒有表格偵測 API**：若 P3 需要把表格獨立成塊，要由文字自行判斷。目前抽出的 Table 2 已是一列一行。
- **比 PyMuPDF 慢約 10 倍**：16 頁約 0.5 秒，相對於嵌入與摘要的時間不是瓶頸。
- **驗證範圍有限**：只測了兩份以 LaTeX 產生、內嵌文字的論文。掃描檔抽不出文字；內嵌圖片中的文字（論文附錄 Figure 4–7）讀不到。

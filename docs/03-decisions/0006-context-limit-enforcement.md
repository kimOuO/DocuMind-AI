# ADR 0006：Context 上限由本地計數規劃、由 Ollama 端強制

- 狀態：已採用
- 日期：2026-11-05
- 對應決策日誌：D33、D55、D56

## 背景

題目規定單次 LLM 呼叫的 prompt 與回答合計不得超過 10,000 tokens。Ollama 沒有計數的端點，而且預設在超量時不報錯：輸入太長會被截短，輸出時 context 用盡會把前面的內容擠掉。所以原本的設計是送出前用本地 tokenizer 精確計數（D33），並以 Ollama 回報的實測值驗證（AC-25）。

實作時把 Qwen3 的 tokenizer 檔內附在專案中（D55），並與 Ollama 模型內嵌的 tokenizer 逐筆比對：詞表 151,669 筆與合併規則 151,387 條完全相同。但 AC-25 的實測仍然發現差異。

## 實驗數據（2026-11-05，Ollama 0.24.0，`qwen3:32b`）

**AC-25 的 15 筆**（五種內容 × 三種長度，本地計數含 chat template）

| 內容 | 約 200 | 約 2,000 | 約 8,000 |
|---|---|---|---|
| 中文 | 0 | 0 | −1 |
| 英文 | 0 | 0 | 0 |
| 中英混合 | 0 | 0 | −2 |
| 程式碼 | 0 | 0 | −1 |
| 多輪對話 | 0 | 0 | −2（首次量測為 −1） |

數字是「本地計數 − Ollama 實測」，負值表示本地低估。11 筆完全相同，4 筆低估 1–2 個 token。

**原因**：以二分法縮小到造成差異的片段，全部含有「同一個字元連續出現三次以上」。Ollama 0.24.0 的 BPE 實作（`tokenizer/bytepairencoding.go`）用堆積依合併規則的優先順序取出下一個要合併的位置，優先順序相同時沒有由左到右的規定；參考實作則由左到右。連續重複的字元會產生多個優先順序相同的合併，兩邊的結果因此不同。詞表、規則與 chat template 都相同，無法靠修正設定解決。

**造成低估的字串**

| 內容 | 本地 | Ollama | 差異 |
|---|---|---|---|
| `(...),` 後接換行 | 2 | 3 | +1 |
| 三個反引號後接兩個換行 | 2 | 3 | +1 |
| `===` 後接兩個換行 | 2 | 3 | +1 |
| `[...],` 後接換行 | 3 | 4 | +1 |
| 連續 8 個 `、` 後接 `（` | 5 | 6 | +1 |
| 20 個連續的 `.` | 2 | 3 | +1 |
| 20 個連續的 `=` | 2 | 5 | +3 |
| 20 個連續的 `_` | 2 | 7 | +5 |
| 40 個連續的 `.` | 2 | 8 | +6 |
| 三個反引號加兩個換行，重複 200 次 | 400 | 600 | +200 |
| `(...),` 加換行，重複 200 次 | 400 | 600 | +200 |
| 目錄的點線（`Section 1 …… 1`）100 行 | 1,080 | 1,280 | +200 |

**沒有差異的例子**：`...`、`---`、`###`、10 個以內的連續 `.`、Markdown 表格的分隔列（100 行，1,000 對 1,000）、Python 的三引號、連續的空白與換行。

**題目指定的論文**：以 pypdf 抽出的 16 頁逐頁比對，本地合計 14,470、Ollama 14,471，差 1。全文有 31 個含重複字元的片段，其中 1 個造成差異。

**方向**：觀察到的所有差異都是 Ollama 較多（本地低估），沒有相反的例子。

**Ollama 在 context 邊界的行為**（把上限設為 2,000 的探測，以及正式上限 10,000 的測試）

| 情況 | 預設 | 加上 `truncate: false`、`shift: false` |
|---|---|---|
| 輸入約 3,000，超過上限 | HTTP 200，悄悄截成 2,000 再回答 | HTTP 400：`the input length exceeds the context length` |
| 輸入 1,924，允許輸出 400 | 輸出 400（前面的內容被擠掉） | 輸出 76 後停止，合計 2,000 |
| 輸入沒有超量 | 正常 | 正常 |

停止原因在串流與非串流下相同：自然結束為 `stop`；達到輸出上限與 context 用盡都是 `length`，以輸出的 token 數是否等於 `num_predict` 區分；輸入超量在產生任何內容之前就以 HTTP 400 拒絕。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| 只加固定緩衝 16（原規則） | 最簡單 | 低估量隨內容成長，固定的緩衝擋不住目錄點線這類內容；超量時仍會被悄悄截斷 |
| 含重複字元的片段改用位元組數保守計數 | 不會低估 | 會高估並浪費額度（40 個點算成 40）；多一套規則要維護 |
| 照抄 Ollama 的合併演算法 | 可以完全一致 | 綁死在特定版本的內部實作，升級後可能悄悄失效 |
| 另外架設與 Ollama 相同的 tokenizer 服務 | 可以完全一致 | 多一個要部署與維護的服務 |
| **固定緩衝 16，加上要求 Ollama 拒絕超量** | 不依賴本地計數完全精確；超量時是明確的錯誤，不是悄悄截斷 | 極端內容下，請求可能被拒絕或回答提早結束 |

## 決定

使用者決定採用最後一項：

1. **本地 tokenizer 負責規劃。** 送出前的預算分配（放幾段證據、預留多少給回答）都用本地計數，加上固定緩衝 16 tokens（`TOKEN_SAFETY_BUFFER`）。
2. **16 tokens 的緩衝不是絕對保證。** 真正防止 context 超量的是 Ollama 端的限制。
3. **每個生成請求都帶** `options.num_ctx`（10,000）、`options.num_predict`（這次呼叫的輸出上限）、最上層的 `truncate: false` 與 `shift: false`。請求只在 `app/llm/ollama_api.py` 一處組裝，有測試檢查其他程式不得自行組裝。
4. **只有自然結束的回答算完整。** 因輸出上限或 context 用盡而停止的回答不得標為 `completed`。
5. **驗收分開。** 本地計數的準確度是 AC-25；請求的參數是 AC-54；伺服器拒絕超量輸入是 AC-55；不捨棄內容、輸出受限、停止原因可判別是 AC-56；帳本與訊息狀態是 AC-57（P2-D）與 AC-08。
6. 不另外建立 tokenizer 服務，不重寫 Ollama 的演算法。

## 後果

- 本地低估到實際超量時，結果是請求被拒絕（HTTP 400）或回答提早停止，並留下帳本紀錄，不會產生根據被截斷內容寫出的答案。
- 被拒絕的呼叫在帳本記為 `failed`、實測值未知，並記為一次低估事件。無法取得實測值的呼叫不得計入實測合規。
- 含大量連續符號的文件在極端情況下可能有請求失敗。目前沒有針對這種內容的處理；帳本的低估事件數可用來觀察是否發生。
- **這些行為在 Ollama 0.24.0 實測。升級 Ollama 之後必須重跑**：
  `pytest -m llm tests/integration/test_token_count_agreement.py tests/integration/test_ollama_context_limits.py`
  特別是合併順序的實作若在新版本改變，AC-25 的差異可能消失或改變方向。
- 更換模型時，要換成對應的 tokenizer 檔並重新比對（見 `app/backend/third-party/qwen3-tokenizer/README.md`）。

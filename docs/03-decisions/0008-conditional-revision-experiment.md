# ADR 0008：條件式驗證導向修正——最多兩次 LLM 呼叫的實驗模式

- 狀態：已採用為實驗模式（預設關閉；是否用於 Demo 由使用者依下列數據決定）
- 日期：2026-11-06
- 對應決策日誌：D68（困境）、D69（決定與設計）

## 背景

P3 的三個必答題在 D63–D68 之後，能用規則抓到的錯誤都能標出來（數字掛錯標籤、全稱結論與表格矛盾、引用頁碼可疑），但 AC-13、AC-14 的通過條件是回答本身正確。D68 後三題各三次：Q3 每次換一種錯（方向寫反、四版本不齊、同行標題下標錯指標），Q2 內容三次都對、引用頁碼三次都錯，提示詞改寫對後者無效。單輪生成加確定性檢查只能提高「可偵測率」，不能提高「正確率」。

限制：每次 LLM 呼叫 prompt＋completion ≤ 10,000 tokens、不截斷；不改檢索、切塊、嵌入；不新增大型框架；不把 key-facts 或論文字面寫進程式；驗收標準不放寬。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| 維持單輪，標示錯誤即止 | 零額外成本；已實作 | AC-13、AC-14 停在 PARTIAL，錯誤只能標不能修 |
| 換更大的模型或開 thinking | 不改程式 | D65 實測 thinking 無改善；更大模型不在環境內，也不保證改善 |
| 收窄回答格式（固定輸出對照表） | 對結構化問題有效 | 為了這份作業特化，接近針對論文寫規則 |
| **條件式修正：初稿 → 確定性檢查 → 有觸發才再呼叫一次修正 → 再檢查 → 依嚴重程度選最終答案** | 用已有的檢查結果當回饋，不靠模型自評；最多兩次呼叫、可開關、預設關；可用 A/B 量測是否值得 | 延遲約兩倍；實驗模式沒有即時串流；觸發只能來自檢查看得到的錯（方向、缺漏大多看不到）；修正稿可能引入新錯 |
| 永遠修正（Always Revise） | 覆蓋檢查看不到的錯 | 成本固定兩倍；沒有回饋時模型可能亂改；只作研究對照 |

## 決定

採第四項為**實驗模式**，預設關閉，單輪 RAG 維持預設：

- `app/chat/revision.py`：觸發項由確定性檢查整理，hard（數字掛錯標籤、全稱結論矛盾、引用不存在的來源編號）與 soft（引用可疑、問題點名的比較對象或消融表的變體未提及）分開記錄，soft 與 completeness 各有開關；未判定不觸發。
- 第二次呼叫的 prompt 含原問題、原來源（同編號）、初稿與逐條檢查結果；輸出上限動態、低於 800 tokens 不修；兩次呼叫各自經 Gateway 的 10K 守門與帳本。
- `choose_final` 依嚴重程度：修正稿有新的 hard 錯誤一律不選；去掉 hard 才算改善；同 hard 下 soft 減少才選修正稿；沒有差別保留初稿；所選答案仍有觸發就標 `unverified`。
- SSE 以 `stage` 事件示進度，最終文字在 `finalizing` 後逐段送出，與預設模式的即時串流分開驗收（AC-04 對預設模式，AC-58 對本模式）。
- 初稿不持久化；研究用的初稿／修正稿對照紀錄只存於 `evaluation/revision-ab/`。
- 是否進 Demo 由 A/B 實驗決定：同一批問題、固定文件與模型設定、同期執行單輪與條件修正，Always Revise 先只做 Q3；以 key-facts 做獨立人工評測（不進 prompt），記最終通過率、修復率、新增錯誤率、觸發率、Token 與延遲。

## 實驗結果（2026-11-06，`evaluation/revision-ab/`）

33 次執行、人工依 key-facts 核對：條件修正把 Q2 的通過率從 0/3 提到 2/3（三次引用錯配都修正、無新增錯誤）；Q1 兩臂都 3/3，但 B 臂三次第二輪都是核對誤報觸發的；Q3 三次都沒觸發、與單輪相同，永遠修正只修到 1 個真錯。觸發題時間 2.3–2.9 倍、tokens 2.1–2.3 倍，33/33 次呼叫 ≤ 10K。

## 後果

- 好處：第一次把「檢查結果」接回生成端；每一次修正都有可追溯的觸發與選擇理由；單輪路徑一行未改。
- 代價：兩倍延遲、無即時串流、三個新開關、一個新事件與一個新欄位；觸發覆蓋不到 Q3 的主要錯誤型態，AC-14 的改善只能從 Always Revise 看。
- 日後要注意：`verified` 不是正確的保證；驗證器與模型都會錯，評測要人工；若 A/B 顯示修正沒有改善或新增錯誤多於修復，實驗模式保留為可開關的研究功能，不進 Demo。

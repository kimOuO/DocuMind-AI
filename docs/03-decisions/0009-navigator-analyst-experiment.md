# ADR 0009：雙角色（Navigator／Analyst）回答模式的實驗

- 狀態：兩輪實驗完成（D71 A/B/C、D73 改良 B），保留為實驗模式（`ANSWER_MODE=roles|navigate`，預設 `single`）；是否用於 Demo 由使用者依下列數據決定
- 日期：2026-11-06
- 對應決策日誌：D70（導航題測試）、D71（設計與確認）、D72（路由前置修正）、D73（改良取證、只重測 B）、D74（涵蓋判定與結構化證據分析、只重測 B3）、D75（事實核對與確定性修正、摘要驗證、只重測 B4）、D76（摘要只存驗證狀態）、D77（Navigator 召回：先量再改，B5 與換模型的 M5）、D78（矩陣第一次進 prompt，B6）

## 背景

D69 的條件修正只對檢查看得到的錯有效，Q3 的錯誤型態（方向、缺漏）與 Q2 的引用頁碼在單輪下仍反覆出現。D70 顯示模型能初步定位「要看哪一節、哪個表」（5 題中 4 題正確）。使用者提出假設：先讓模型當 Navigator 指出證據位置，再當 Analyst 依實際取回的證據分析，可能比單輪更完整、更正確；並要求分離「角色分工」與「中途重新取證」兩個變因。

限制同前：每次呼叫 ≤ 10,000 tokens；不改檢索、切塊、嵌入；不寫死論文字面；key-facts 不進 prompt；單輪預設不變。

## 考慮過的選項

| 選項 | 優點 | 缺點 |
|---|---|---|
| 維持單輪 | 零成本 | Q2／Q3 的既有缺口不變 |
| **A：單次呼叫、同 prompt 兩角色** | 零額外呼叫；只量角色指令策略的效果 | 證據沒變，Navigator 列出的位置若不在來源裡也拿不到 |
| **B：先導航呼叫、程式補取、再分析呼叫** | 能補到 Top-K 沒拿到的位置（附錄表、第 10 頁文字） | 兩次呼叫、延遲約兩倍；計畫可能指錯；補取可能擠壓預算 |
| 完整 agent 框架（工具呼叫、多輪規劃） | 更靈活 | 違反最小改動；不可控的呼叫數與 token |

## 決定

實作 A、B 為實驗模式（`ANSWER_MODE=roles|navigate`，預設 `single`），C 為現行單輪基線：

- 文件地圖取自系統已有的東西：章節摘要的標題與頁碁範圍、切塊裡的表／圖標題行；不含論文字面。
- Navigator 的輸出是候選閱讀計畫：每條對照地圖定位，定位不到的不取證、只記數。
- B 以原始 Top-K 為基礎，計畫取回的切塊排在後面、在預算內依序納入，逐塊記錄保留／重複／超預算；Analyst 的 prompt 把計畫標為「候選、未驗證」。
- 摘要路線（Q1）三臂共用預存摘要為基底；B 的補取切塊附在摘要之後。
- 路由（D72）三臂共用；兩次呼叫各守 10K、各記帳本；`stage: navigating` 事件；單輪 SSE 不變。
- 評測 `evaluation/navigator-abc/`：Q1、Q2、Q3、G1、G2 各臂 3 次；真值 `ground-truth/evidence-locations.*`；量 Location Recall（Top-K／計畫／最終來源三層）、Evidence Coverage（最終來源文字含關鍵片段）、Answer Pass Rate（人工 key-facts）、Citation Support（人工頁級）、計畫定位率、補充量、多餘證據、token、延遲。
- 結論的嚴謹度：A 對 C 量角色指令策略整體效果；B 對 A 同時差呼叫數、prompt 與取證，只能評估導航取證流程整體效果；三次為初步探索。

## 實驗結果（2026-11-06，`evaluation/navigator-abc/`，45 次執行）

人工依 key-facts 判定的通過率（嚴格標準）：C 5/15、A 7/15、B 5/15。逐題：Q1 2／2／1（三臂共用的章節摘要含一句錯誤，核對四次都抓到）、Q2 0／2／2、Q3 0／0／0、G1 3／3／2、G2 0／0／0。含事實性錯誤的次數 C 2、A 4、B 6。

- **A 對 C**（證據相同）：差別只在 Q2——A 三次都把第 10 頁的更新機制引對 [5]，C 三次引錯 [3]；其餘四題持平。成本＋8% 時間、＋16% tokens。三次內不足以斷言是角色指示的效果。
- **B 對 A**：唯一的證據改善在 Q2（Coverage 0.50→1.00，補到 Table 1），通過率與 A 相同；G2 三次都定位到第 26 頁的 Table 6（計畫 Recall 1.00），卻因預算先到先得被排除（最終 Recall 0.00）；Q3、G1 補的全是多餘證據（整體多餘比例 73/85）；Analyst 拿到更多表格文字後寫更多數字、錯得也更多。成本 2.1× 時間與 tokens。
- 核對器在這批資料上：抓到 Q1 的 54.4%×4、A-Q3-1 的 80.8%、Q2 的四次引用錯頁；誤報 B-Q2-2 的「…, respectively」句型 4 個；漏掉 B-Q2-1 的兩個對照方寫錯、B-Q3-3 的定義與方向寫反。

## D73 改良取證（2026-11-06）

A/B/C 的結果指出 B 的失敗在取證機制而非 Navigator：使用者寫成任務書（決策日誌 D73），只改 B、只重測 B。改動：

- 地圖到子章節：查詢時用 AC-53 的標題辨識掃切塊裡的編號標題行，得每節的起迄切塊、起迄頁與父節（下一個標題在某塊第一行則該塊不共用；切塊重疊造成的重複標題只算一次）；沒有標題的文件退回章節摘要。
- Navigator 輸出目標而非位置：`位置 | need | priority | status`（也接受 JSON），並看得到原始來源的章節、是否為表格與片段。
- 範圍內語意排序：每個目標的候選限定在其切塊範圍（或頁），由 pgvector 以「與問題、與 need」兩個餘弦相似度的平均排序；問題向量沿用檢索那一次，need 向量一次批次嵌入、失敗退回只用問題向量；表／圖目標依結構直接取標題行所在切塊與其後討論（D62）。
- 預算輪流：required 先、下一候選分數高者先、表格最先；每目標至多 3 塊；較大分數未達 `MIN_SIMILARITY` 的不配額；放不下的記「超預算」換下一目標；全域去重。
- 可觀察性：`done.navigation.items[]` 加 need／priority／status／label／candidates／selected／excluded，頂層加 budget／evidence_tokens／embedding；`log[]` 加 target／score。既有欄位與單輪模式不變。

### D73 的結果（2026-11-06，`evaluation/navigator-abc/` 的 `B2-*`，15 次；C、A、舊 B 為歷史紀錄，探索性比較）

B2 通過 8/15：Q1 3/3（摘要本批重生、不可直接比）、Q2 3/3、Q3 0/3、G1 1/3、G2 1/3；含事實性錯誤 5 次。機制面：90 條目標全部定位（含子節）；G2 的 Table 6 兩次進入 Analyst 的 prompt（舊 B 零次），一次答對；Q2 第 10 頁的更新證據不被擠掉；重複的不再加。沒改善的：多餘證據 90%（低相關門檻幾乎不起作用，bge-m3 的同篇相似度多在 0.45 以上；多餘來自 supplementary 目標）；Q3 證據早已齊全、答案仍缺格（生成問題）；G1 兩次把 News 的 units 抄成 Podcast 的 34（退步，疑與多補 6–8 塊有關，三次不能斷定）。成本與舊 B 相當（7,695 tokens／29.4 秒，單輪的 2.3×／2.1×）。

## D74 Coverage-Aware Retrieval ＋ Structured Evidence Analysis（2026-11-06）

B2 顯示位置能準確變成證據，但多餘證據仍 90%、多補文字反而抄錯、證據齊全仍答不齊。使用者的任務書（決策日誌 D74）分兩部分，只改 navigate 模式、不加呼叫：

- **Coverage**：取證前依結構判定每個目標被原始來源涵蓋的程度（表／圖看標題行所在切塊是否在來源且含表格列；子節看切塊範圍；只知頁碼者 unknown），required 且 covered 的不取，全部 required 都 covered 時 supplementary 一律不取；選取分兩階段（required 先、supplementary 用剩餘預算、全題上限 2 塊、字面重疊高者視為重複）；required 沒進 prompt 的記 `unmet_required`。
- **Evidence Matrix**：資料來源是入庫時已逐格改寫的表格切塊（`cells_of`），不另建資料表、不用真值檔；每格記來源、頁、表、群組、列、欄、同列同區塊配對的另一欄、值、單位、由標題通用量測詞推得的方向（否則 unknown）。哪一欄是「方法」哪一欄是「對照」無法通用判定，只記配對。沒被切成表格切塊的表（GraphRAG 的 Table 6）沒有 Matrix，prompt 標明無結構化資料。方法定義只取「方法名＋操作動詞」的原文句。
- **檢查**：方向核對（同句兩數字、同群組且同列或同欄、同配對、方向已知才判 inconsistent）與完整性（問變體且表有 ≥2 變體欄時要求某一條件下全部方法的值）加入既有的 `_assess`，四態 `analysis_status` 進 `done`；單輪模式只多了 payload 欄位，回答文字不變。

### D74 的結果（2026-11-06，`evaluation/navigator-abc/` 的 `B3-*`，15 次；歷史紀錄為探索性對照）

整體通過 7/15（Q1 1、Q2 2、Q3 0、G1 3、G2 1），事實正確 9/15、完整 13/15。Q3 三次都給出同條件四版本、160 個數字全對、定義全對（歷史零次完整），剩下的錯全是比較方向措辭；方向核對因 Table 2 標題沒有通用量測詞而只能回報 uncertain。Q1 兩次錯在本批重新產生的摘要原句（Summary Quality）。G2 零事實錯誤、Table 6 進了 1/3；G1 回到 3/3。涵蓋判定在 Q3 把補充降到 0，但 GraphRAG 的表沒被切成表格切塊、整節目標只能判 partial，多餘證據仍 89%；supplementary 上限 2 塊有效。成本 7,532 tokens／40.9 秒。單輪仍為預設；下一步建議：方向推法（成對百分比合為 100）、摘要產生時的數字核對。

## D75 Analyst 事實核對與修正、摘要驗證（2026-11-06）

B3 剩下的錯在生成端（方向措辭寫反、把 NaiveRAG 數字當 GraphRAG）與摘要端（摘要原句把 NaiveRAG 的值歸給 -High）。使用者的任務書（決策日誌 D75）要求把數值大小、指標方向、效能結論分開核對，修正不得造數，摘要存入前驗證。改動：

- 方向核對分成數值大小詞（算術判定）與效能詞（需方向）；方向除標題量測詞外，成對百分比合為 100 只作輔助訊號，須加來源文字的量測詞才推為 higher；方向 unknown 時 Analyst 被要求用中性大小詞。
- 方法別名由定義句抽出，核對器認得「removing high-order retrieval」是 -High。
- 確定性修正（`correction.py`）：反義詞、換名（名字寫在數字後）、換值（主詞寫在數字前且表格恰有一格）、否則刪括號或整句；一輪、再核對。navigate 模式改為生成→核對→修正→送出；章節與全文摘要存入前做同一套核對與修正。
- 不加 LLM 呼叫；單輪模式只多 `correction: null`。

### D75 的結果（2026-11-06，`B4-*` 與修復後的 `B4b-*`，各 15 次；歷史為跨批次對照）

B4 3/15（事實正確 5、完整 12）、B4b 8/15（8、13）；B3 為 7/15（9、13）。自動修正合計：正確 3 次（一處 86.4%→73.6%、一處 54.4%→48.4%、刪一句錯的 67.6%），有害 5 次（B4 摘要把兩處變體名換成 LightRAG；B4b 一次把數字全對的 48 格表格改錯、一次刪掉 15 句大多正確的句子、一次刪掉 GraphRAG 全文摘要第一段），無效 1 次。原因是修正依賴的宣稱解析（D67 的子句方法歸屬規則）在列表句、兩欄表格、雙主詞句上會歸錯方法；核對只附註時無害，變成修正就改壞文字。方向核對 30 次回報 0 條，人工看到的方向錯全部漏判。**處置**：自動修正不套用於正式流程——核對照跑並只回報（回答的 `done.correction`、摘要的驗證紀錄），文字不動；保留別名、大小詞／效能詞分開、方向來源、摘要存入前的核對紀錄與摘要呼叫重試。實作方式（設定旗標或移除修正）在 D76 定案。navigate 模式仍為實驗模式、預設單輪。

## D77 Navigator 召回：先量再改（2026-11-07，B5 與換模型的 M5；另一工作階段執行，紀錄在 README 的 D77、M5 節與決策日誌 D77）

離線數 B2–B4b 的 48 份計畫：Q2 需要的 Table 1 只有 5/12 次被列、G2 的 Table 6 只有 6/12 次，而兩張表從不在 Top-5 裡——沒列就等於 Analyst 看不到；Q3、G1 的表每次在 Top-5 也每次被列。Navigator-only 工具（只做第一次呼叫）量四種設定後選 N4：Navigator prompt 加「標題與問題相關的表都要列」、Navigator 呼叫 temperature 0（`NAVIGATION_TEMPERATURE`，只作用於該呼叫，仍經預算守門與帳本）。

- **B5**（使用者決定：以 B3 的模型輸入為基準、D75／D76 的 prompt 變更停用、修正器不動作，只加 N4）：6/15（Q1 0、Q2 1、Q3 0、G1 3、G2 2；B3 7/15），事實正確 6、完整 12。Table 1、Table 6 三次都進到 Analyst（B3 的 Table 6 只有 1/3），G2 由 1/3 到 2/3。Q2、Q3 共 336 個表格數字全對，錯全在散文的方向句（五句）、G2-1 選錯 Table 6 的列、Q1 三次照抄摘要錯句（Summary Quality）；Q3 三次缺 -Low、-Origin 的定義句（抽取只抓到 -High）。
- **M5**（同 B5、換 `qwen3.6:27b`）：6/15（Q1 1、Q2 1、Q3 1、G1 3、G2 0），事實正確 6、完整 11。數字全對、方向句錯只剩一句全稱句，Q3-3 是歷史上第一次 Q3 事實與完整同時通過；代價是冗長（兩次撞到 2,500 輸出上限、推理寫進答案、Q2 貼著 10K），且 Navigator 在 temperature 0 下三次都沒列 Table 6，G2 掉到 0/3。換模型暴露並修了三件系統問題：tokenizer 不同（`TOKENIZER_PATH`／`TOKENIZER_SHA256`、`third-party/qwen3.6-tokenizer/`）、摘要超限重試改兩次、誤覆蓋根目錄 README 已還原。

結論：Navigator 這層以 N4 可以穩定列出需要的表（qwen3:32b 下三次全中），取證的上限不再卡在 Navigator；剩下的錯集中在 Analyst 的散文方向句與摘要原句，方向核對仍回報 0 條。預設仍為單輪。

## D78 Evidence Matrix 第一次真的進到 Analyst（2026-11-07，B6；README 的 D78 節）

追蹤一次中文 Q2 的兩級 prompt 全文後發現：矩陣的 token 預算 900 低於一張完整結果表排成矩陣的 1,348 tokens，超過即整張略過，略過分支又把表名丟掉改說「讀不到表格資料」。預算與格式自 D74 未變，B3–B5 的 Q2、Q3 每次矩陣都是完整表，**所以 D74 的矩陣在 B3、B4、B4b、B5 四批裡從未進過模型輸入**，只有答後核對用到它；單元測試用字數計數器與小表格，未暴露。這是 AI 跨四批實驗未發現的系統性失誤，先前「B3 的矩陣效果」的解讀都要打折。

修正（8c82629）：預算 1,500（一張表加餘裕）；略過時點名略過的表；因守門是 prompt＋2,500 ≤ 10,000，矩陣的空間從 navigate 模式的補取預算扣除；紀錄新增 `shown_tokens`、`left_out`、`retrieved_tokens`。

B6（同 B5 設定，只有矩陣進 prompt；Q2、Q3 各 3 次）：矩陣六次都送出（1,348 tokens）；六次 416 個表格數字逐格與配對全對，B5 的「拿錯區塊的 LightRAG 數字」沒再出現；人工判定 Q2 2/3（B5 1/3）、Q3 1/3（B5 0/3；B6-Q3-3 是程式判定 SUPPORTED_AND_COMPLETE 第一次與人工通過一致）。剩下的錯全是全稱結論句，Q3 的集中在跨配對比較（變體對 LightRAG，各以 NaiveRAG 為對照），全稱檢查對這類句子沒有覆蓋；核對器另有兩種誤報（「regresses」方向讀反、「A slightly outperforms B (a vs b)」兩數互換）。3 對 3 的差距在噪音範圍內，能說的是錯誤型態從配對錯變成全稱句錯。代價：Q3 每次多約 1,000 tokens，補充塊減半。預設仍為單輪。

## 後果

- 好處：第一次把「位置」當成一個可量測的中間產物（計畫定位率、Recall 三層）；補取是結構性的（頁、表），不是再做一次相似度搜尋。
- 代價：navigate 模式兩次呼叫、新事件與欄位、三個新開關之外再加一個；地圖依賴章節摘要已完成（沒有摘要時只有表／圖）。
- 日後要注意：Navigator 指錯位置時只是浪費預算、不會變成錯證據（定位不到的不取）；但「定位到了、內容卻不是答案需要的」會變成多餘證據，要用多餘證據比例看。實驗證實這正是 B 的主要問題（多餘 86%、G2 的 Table 6 被排除）。若再試 B，先改：補取切塊依問題相似度重排（每條計畫 2–3 塊）、各計畫項輪流配額、地圖細到小節。
